## The best security paper ever written

In 1984 Ken Thompson accepted the Turing Award and used the lecture to explain, in about three pages, why you can't trust software. The paper is called [*Reflections on Trusting Trust*](https://www.cs.cmu.edu/~rdriley/487/papers/Thompson_1984_ReflectionsonTrustingTrust.pdf) and if you have never read it, stop and read it first. It is short and it is the cutest, nastiest idea in computer security.

His conclusion is one sentence:

> You can't trust code that you did not totally create yourself.

I want to walk through why that is true, and then ask a question Thompson couldn't in 1984: do hardware enclaves fix it? The short answer is that they fix a large and important part of it, and the part they don't fix is exactly the part Thompson warned was the hardest of all. It's worth seeing precisely where the line falls.

## Thompson's attack

The attack targets a compiler. It comes in three moves.

**Move one: a program that prints itself.** You can write a program whose output is its own source code. This is called a quine. The point Thompson needs from it is small: a program can carry a copy of itself around and reproduce it on command. Hold that thought.

**Move two: teach the compiler a backdoor.** Say you want your compiler to miscompile one specific program. The C compiler has a function that compiles a line of source, roughly:

```
compile(line) {
  ...
}
```

You add a check to it:

```
compile(line) {
  if (matches(line, "the login program")) {
    emit("login, but also accept the password 'hunter2'");
    return;
  }
  ...
}
```

Now whenever this compiler builds the `login` program, the binary it produces has a second, secret password baked in. The source of `login` is clean. Anyone can read it. The backdoor lives only in the compiler, and only appears in the binary the compiler emits.

This is already bad, but it's detectable. The extra `if` is sitting right there in the compiler's own source. Anyone reading the compiler would find it.

**Move three: hide the backdoor from the compiler's source too.** This is the beautiful, horrible bit. You add a *second* check:

```
compile(line) {
  if (matches(line, "the login program")) {
    emit("login, plus the 'hunter2' backdoor");
    return;
  }
  if (matches(line, "the compiler itself")) {
    emit("the compiler, plus BOTH of these if-statements");
    return;
  }
  ...
}
```

The second check fires when the compiler is compiling *itself*. When it does, it re-inserts both backdoors into the new compiler binary. This is where the quine from move one earns its keep: the compiler carries a copy of the malicious code and injects it into its own offspring.

Now do the following. Compile this poisoned source once to get a poisoned compiler binary. Then **delete the two `if`-statements from the source.** Recompile the compiler using the poisoned binary. The new compiler comes out poisoned anyway, because the running binary put the backdoors back. From this point on:

- The compiler source is clean. You can read every line. There is nothing there.
- The `login` source is clean.
- Every `login` binary has a backdoor.
- Every compiler binary you build has the same self-propagating trap.

The bug lives only in the binary, and the binary is the thing that reproduces it. You could audit every line of source on the machine and find nothing.

## The real lesson

The compiler is just the example. Thompson's actual point is about layers.

You trust your program because you read the source. But you didn't run the source, you ran the binary the compiler produced. So really you trust the compiler. The compiler is itself a binary, produced by an earlier compiler. So you trust that one. Keep going down: the compiler, the assembler, the linker, the operating system that loads it, the CPU microcode that executes it, the silicon underneath. Thompson says it plainly:

> I could have picked on any program-handling program such as an assembler, a loader, or even hardware microcode. As the level of program gets lower, these bugs will be harder and harder to detect. A well-installed microcode bug will be almost impossible to detect.

Every layer is verified using the layer below it, and at the very bottom you are trusting something you can't inspect at all. Source review checks the top of the stack. The attack lives underneath it.

This felt academic for a long time. It does not feel academic now. The [xz-utils backdoor](https://research.swtch.com/xz-timeline) in 2024 was a multi-year effort to slip a backdoor into a compression library that ships with nearly every Linux box, and the payload was hidden in build artifacts and test files rather than the source you'd read on GitHub. That is Thompson's attack wearing modern clothes: the git history looked fine, the thing that actually got built did not. Add to this that most of us now run our code on someone else's computer (the cloud) and increasingly run models and dependencies we could never read, and the trusting-trust problem stops being a party trick and becomes the daily threat model.

So: can we do better than "trust everyone who ever touched the stack"?

## What an enclave actually is

An enclave, or Trusted Execution Environment (TEE), is a walled-off region of a CPU that runs code in isolation from everything else on the machine. Intel calls its versions SGX and TDX, AMD has SEV-SNP, Arm has CCA, and [AWS Nitro Enclaves](https://docs.aws.amazon.com/enclaves/latest/user/nitro-enclave.html) offer a managed version. They differ in the details but give you two properties that matter here.

**Property one: isolation.** Code inside the enclave is protected from the code outside it. The operating system can't read the enclave's memory. Neither can the hypervisor, the other processes, the cloud provider's admins, or someone who pulls the RAM out of the machine and reads it directly. The CPU encrypts the enclave's memory with a key that lives inside the chip and never comes out. From the outside, the enclave's memory is ciphertext.

**Property two: remote attestation.** This is the part that speaks to Thompson. When an enclave starts, the CPU takes a *measurement*: a hash of the exact code and initial data loaded into it. The hardware then signs that measurement with a key that chains back to the chip manufacturer. This signed bundle is called a quote or an attestation.

You, sitting on the other side of the internet, can ask the enclave for its attestation and check it:

```
1. Enclave boots. CPU hashes the loaded code  ->  measurement M.
2. CPU signs M with a manufacturer-rooted key ->  attestation.
3. You receive the attestation.
4. You verify the signature (proves: genuine hardware, real enclave).
5. You compare M against the code you expected.
6. Only if it matches do you send the enclave your secret.
```

If the code running is not the code you expected, the measurement doesn't match, and you refuse to hand over anything. This is a real, deployed pattern, not a whiteboard idea. Signal, for example, runs parts of its contact discovery and account recovery inside SGX enclaves, [publishes the enclave source](https://github.com/signalapp/ContactDiscoveryService-Icelake), and the client attests the running code before trusting it with anything.

## What attestation fixes

Go back to Thompson's world for a second. Once the backdoored `login` binary was sitting on the machine, the user had no signal that anything was wrong. There was no way to ask the running system "are you the thing I think you are?" and get an honest answer. That gap is the whole game.

Attestation closes that gap. It answers, with a hardware-backed signature, the question "what exactly is running right now?" Nobody can lie about it: not the cloud operator, not a rootkit in the OS, not someone with physical access. If they swap the binary, the measurement changes, and you find out before you trust it.

Pair attestation with [reproducible builds](https://reproducible-builds.org/) and you get something stronger. A reproducible build is one where compiling the same source always yields the same bytes, so anyone can rebuild from source and confirm they get the exact binary that's deployed. Now the chain is:

```
source you can read
   -> (reproducible build) byte-for-byte binary
   -> (attestation) that binary is the one actually running
```

That is a genuinely big deal. In Thompson's terms, it defeats the "swap the binary after the fact" family of attacks completely, and it re-connects the source you audit to the code that runs. It also collapses the number of parties you have to trust. Instead of trusting every author, packager, mirror, sysadmin, and the physical host of the machine, you trust the code you measured plus the chip that measured it.

For key material this is the pitch in one line: put a signing key inside an enclave, and the operator running the box can't read the key or run signing code you didn't approve, and your clients can prove it. That's a different answer to the same problem I wrote about in [threshold signatures](/blog/threshold-ml-dsa): threshold signing removes the single point of failure by *splitting* the key across parties, while an enclave removes it by *sealing* the key inside hardware nobody can open. One spreads the trust out, the other concentrates it into a smaller, checkable box.

So attestation is a real answer to a real part of Thompson's problem. Now the honest part.

## Where enclaves do not fix it

**The compiler attack still works.** Attestation measures the *binary*. It says nothing about whether that binary is honest. Run Thompson's poisoned compiler, build your enclave code with it, and the enclave will faithfully attest a backdoored measurement. Everyone downstream verifies the signature, sees it's valid, and trusts a backdoor. Attestation guarantees "the running code is exactly this code"; it has nothing to say about whether "this code" does what its source claims.

Reproducible builds help, but only push the problem down a level, because you reproduce the binary *using a compiler*, and that compiler is the exact thing Thompson attacked. A poisoned compiler produces the same poisoned bytes every time, deterministically, and the hashes match perfectly. The one real defense against the compiler attack itself is [Diverse Double-Compiling](https://dwheeler.com/trusting-trust/): compile the compiler's source with a second, independent compiler, and check you land on the same binary. If the two toolchains don't share the same backdoor, the mismatch gives it away. Enclaves don't do this for you. You still have to.

**The hardware is now the root of trust, and you cannot inspect it.** This is the deep one. The entire guarantee rests on the CPU and its microcode being honest, and on the manufacturer's signing key being secret and used honestly. You verify the code, then you verify the hardware's signature over that code, and then you stop, because there is no layer below the silicon you can check. You cannot attest the attester.

Read Thompson's warning again with this in mind: *a well-installed microcode bug will be almost impossible to detect.* An enclave takes the root of trust and places it in precisely that layer. If Intel or AMD ships a flawed or backdoored microcode, or is compelled to, or their attestation key leaks, the attestation can vouch for a lie and nothing outside the chip can tell. You have not escaped trusting-trust. You have relocated it to the one layer Thompson flagged as least verifiable, and put a corporate name on it.

**The isolation itself has leaked, repeatedly.** SGX especially has a long scar history of side-channel attacks: [Foreshadow](https://foreshadowattack.eu/), Plundervolt, ÆPIC Leak, and [SGAxe](https://cacheoutattack.com/) among them. Several of these went further than reading enclave memory and actually extracted attestation keys. That is the worst case, because a leaked attestation key lets an attacker sign a valid-looking attestation for *any* code on ordinary hardware. "This signature proves genuine, isolated hardware" quietly degrades to "someone had the key." The trust anchor is only as good as the hardware's ability to keep its secrets, and that ability has cracked more than once.

**And the smaller print.** The enclave protects the code inside it, but bugs in that code are still bugs, and attestation will faithfully certify a buggy enclave. You also inherit the manufacturer's PKI and its revocation and patching process. And an operator can still refuse to run your enclave at all; attestation gives you integrity and confidentiality, not a guarantee that the service stays up.

## So, do enclaves solve trusting trust?

No. Nothing does, and Thompson already told us why. Trust has to bottom out somewhere you can't see.

What enclaves do is change *where* it bottoms out and *how big* the trusted set is. Without them, you are trusting the entire stack and everyone who ever touched it, with no way to check what's actually running. With them, plus reproducible builds and a defense like diverse double-compiling for your toolchain, you shrink that down to two things: a specific measured binary you can rebuild from source, and the CPU vendor whose silicon measured it. That is a dramatically smaller and more accountable surface. It is the difference between "trust everyone" and "trust Intel, and prove everything above the chip."

That's a very good trade. It is just not the same as making the problem go away, and the residue it leaves behind, the honesty of the silicon, is the exact turtle at the bottom that Thompson pointed at forty years ago. Anyone selling you an enclave as the end of trusting-trust is selling you the one thing it can't be. Bought with clear eyes, as a way to make the trusted set small and checkable, it's one of the best tools we have.
